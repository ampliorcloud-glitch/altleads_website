4 · Email relay: WHO physically carries our mail (replaces Brevo idea) AWAITING YOUR PICK

Ankit 2026-07-03: "brevo is not free… I want in such a way where I control everything, can we not do what brevo is doing?" — engineered 3 real options.

S1 · Google Workspace SMTP relay — ₹0, you already own it

You pay for Google Workspace (amplior.com) already. Workspace includes an SMTP relay (smtp-relay.gmail.com): our CRM hands mail to Google, Google delivers it as any user on YOUR Workspace domains. hungerbox.co.in gets added to your Workspace as a secondary domain (you own it → 10-min, free). SPF/DKIM = Google's own, enabled from your Admin console — real DNS records, today, no new vendor.
✓ ₹0 · ✓ you control it in YOUR admin console · ✓ Google-grade deliverability
✗ daily caps (~10k relay recipients/day org-wide — far above beta needs)

S2 · Amazon SES — pay-per-use, no subscription

No monthly fee ever: ₹~9 per 1,000 emails, prepaid nothing. Full API control, per-domain DKIM, bounce webhooks (feeds ALT-512 guardrails). Needs an AWS account + a one-time "production access" request (1-2 days).
✓ cheapest at scale · ✓ webhooks for bounce/complaint automation
✗ new vendor account · ✗ pay-per-use (tiny, but not zero)

S3 · Self-host our own mail server (true "be Brevo")

Run an open-source mail server (e.g. Postal) on our own droplet. Zero per-mail cost, absolute control.
✗ DigitalOcean blocks port 25 (support ticket) · ✗ WE own IP warm-up, blocklist fights, reverse-DNS — a part-time ops job that hurts deliverability vs S1/S2 · not recommended until volume is huge
Recommendation: S1 now (₹0, your own console = the control you asked for), S2 later if volume outgrows caps or we want bounce webhooks. Reply "email S1" / "S2" / "S3".

7 · Sell the CRM to other companies (multi-tenancy) DECIDED 2026-07-06 — T2

Ankit 2026-07-06: "invite a new user as separate total account… who can use CRM as their own… data we can control if they can see ours or not, but can deliver blank as well. We want to sell this to other companies." MOTIVE: a sellable product where customer data is isolated (blank start) and OUR data is never exposed.

T1 · Instance-per-customer (fallback if T2 timeline pinches)

Each customer gets their OWN copy: separate Supabase project (their own empty database + logins) + their own app on our Dokploy server (their subdomain, e.g. crm.customer.com). We already have the launch runbook — the CRM test instance was deployed exactly this way.
✓ sellable now, zero code changes · ✓ STRONGEST isolation — their data physically separate, ours untouchable · ✓ per-customer pricing/branding easy
✗ ops per customer (updates deployed per instance) — fine to ~10-15 customers
⚠ Consequence-if-wrong: at 30+ customers, per-instance updates become a maintenance treadmill → mitigate by scripting fleet deploys via the Dokploy API (we already drive it by script); detect = time-per-release climbing.

T2 · True multi-tenant (one app, tenant_id everywhere)

The HubSpot/Zoho architecture: ONE database, every table gets a tenant_id, RLS isolates every query. One deploy serves all customers.
✓ scales to thousands of customers · ✓ one update updates everyone
✗ BIG retrofit: ~65 tables + every RLS policy + every query re-audited
⚠ Consequence-if-wrong: ONE missed tenant filter = customer A sees customer B's (or OUR) data — a trust-ending breach of the exact motive. This is why it needs a dedicated hardening phase, not a quick bolt-on.

T3 · Hybrid path (recommended sequence)

T1 now for the first paying customers (revenue + learning, zero risk), and design every NEW feature tenant-aware; do the T2 retrofit only when customer count demands it, as a planned project.
✓ revenue first, architecture debt paid when justified
⚠ Consequence-if-wrong: if T2 never gets scheduled, we fossilize into unscalable per-instance ops → mitigate with an explicit customer-count trigger (e.g. "at 8 paying customers, start T2").
Ankit's decision (2026-07-06): T2 — "similar to Zoho/HubSpot, until it becomes issue. Plan for same." ADR-36. Phased plan in ALT-522: P0 tenant registry + every NEW table born with tenant_id · P1 retrofit tenant_id + RLS across existing ~65 tables (staged, table-by-table, throwaway-login validated) · P2 tenant provisioning/invite flow (blank org, admin seed) · P3 tenant-scoped settings/branding/billing hooks. ⚠ Standing consequence: one missed tenant filter = cross-customer data breach — every P1 table ships with an isolation test, no exceptions. Sequenced AFTER internal beta stabilizes (it must not destabilize launch).
